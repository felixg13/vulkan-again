## Current Architecture
The current engine is based on https://github.com/SaschaWillems/HowToVulkan and https://github.com/milkru/vulkanizer i sourced insipiration from vulknizer for light abstraction of buffers and followed sascha willems for the rest of the engine. The current architecture is a monolithic design that tightly couples the renderer with the scene loading and material binding logic. This makes it difficult to extend the renderer to support more complex scene loading and material binding scenarios.

## Questions
Here's what I would like to abstract but i am wondering if it would fall apart when handling a varity of scenes:

Pipeline: I think we should be able to do the pipeline creation once per creation of the engine, I am not planning to handle every sprim and gprim of hydra, focusing only on mesh and material binding. We will author usd files accordingly to the renderer capabilities. That means we could handle the whole scene with a singular set of shaders, is this too restrictive or realistic for a simple renderer? If possible we could extract the pipeline creation in seperate class that configures it's own layouts according to a vertex and material struct. Bascally we have two questions here: Is one pipeline realistic for our hydra end goal? Is possible to abstract the pipeline creation away from main.

Data driven pipeline layout: I want to use materialx shadergen for complex and simple (at first) materials, which means we cannot assumeanything about the material layout, therefore we need to refactor the pipeline creation to be driven by the shaderGraph generated by the materialx shadergen. This means we will need to create a system that can dynamically generate pipeline layouts based on the material definitions provided by MaterialX. The shader gen will use slang as a target for generation https://www.aswf.io/blog/materialx-adds-support-for-slang-shader-generation/
Since we are in a view only context we should use the slang reflection to generate our layouts, or do we still need to use the ShaderGraph from materialX? 
since we are targetting usd at the end of the day would be be better of using pxr/imaging/hdMtlx instead of Materialx deirectly.
For debug purposes we propably don't want to restrict ourself to the mtlx hydra render context and still handle the surface preview context. that means we should also have a uber shader in slang that can handle pbr. How do we abstract those two material paths in order to keep the pipeline layout creation generic and flexible enough to handle both cases?
